# Dig architecture

Dig is a self-contained local Codex plugin named `dig` (plugin id `dig@dig`; the repository is also `dig`): a bundled Node MCP server, also named `dig`, two native MCP App resources (the library and an inline saved-research card), and source-specific skills for ordinary workers or inline use. Version 0.2.31 carries the source catalog of the original Dig edition forward. `src/version.mjs` is the one version source for the server, both views and the preview; the build refuses a package or plugin manifest that disagrees with it.

## Boundaries

- The installed package needs Node 22+, not npm, Bun, node_modules, OMP or the existing Dig checkout. Development uses npm and esbuild; TypeScript is bundled before installation.
- `.agents/plugins/marketplace.json` names the marketplace `dig` (so the plugin id is `dig@dig`) and points at `./plugin`. Codex owns its installed cache copy. Change source, build, bump the package version and install through Codex; never edit the cache.
- Default native state is `~/.local/share/dig`. `DIG_STATE_DIR` selects isolated state. Updates do not relocate or rewrite research. The package never implicitly reads another Dig edition's configuration, keys, library or Papers checkout.
- The initiating thread chooses the source methods and each ordinary worker's model/effort. It can run a method itself. There are no generated agent definitions, mandatory persistent workers, master composer or orchestration service.
- A worker knows only its assignment: not the initiating conversation, the files that thread read or what the user already settled. Codex 0.160.0's spawn tool description says a full-history fork keeps the parent's model and effort and accepts no override, and that choosing a model or effort needs `fork_turns` of `none` or a turn count; so a worker that follows `workerDefault` receives at most the turns the parent chose to fork (read from the CLI binary's tool text on 2026-10-05, not observed in a live spawn). The `dig` skill therefore has the initiating thread write a self-contained assignment (the question's purpose, what is already known, scope, names and terms, files and saved reports to read, the user's explicit method choices, and any context that must stay out of provider queries) beside the date, project, dig id and `skillPath`. The method's skill, not the assignment, decides how to search. Each source skill tells a worker to read what its assignment points to and to state its assumptions and missing context in the report's `## Summary` and its return. Inline runs already hold the context.
- Source workers return saved report paths. The initiating thread reads every report it relies on in full and checks load-bearing claims against retained originals; a pointer or worker summary is not proof of reading.
- The UI reads and inspects evidence. Questions stay in Codex's native composer; Dig has no duplicate question or attachment controls and never launches research from its UI.

## Source catalog and execution

`src/providers/modules.ts` owns the source and method identities. There are **21 catalog entries**, each a report source. X has three independent methods, giving **23 source-method skills**. The YouTube transcript helper, the `dig` and `library` guidance and the `setup` onboarding skill bring the packaged skill count to **27**. Skill directories, skill names and method names are the same word (`hackernews`, `x-judge`, `youtube-summarizer`); Codex lists each as `dig:<skill>`.

### Skill packaging and invocation

- Each skill carries `agents/openai.yaml` with a display name (`Dig · <Source>`), a short description, a glyph tile icon, the brand color and a default prompt. The tiles under `plugin/assets/skills/` are generated by the build from `src/glyphs.mjs`, which holds Lucide glyph data (ISC; `plugin/Lucide-LICENSE`). Icon paths are `../../assets/skills/<glyph>.svg`; Codex resolves them inside the installed plugin's `assets/`.
- The 23 source-method skills and the YouTube helper set `policy.allow_implicit_invocation: false`. Codex then leaves them out of the model's skill list; the designed route is `dig` → `source_info` → each method's `skillPath`, and workers load skills by path. Only `dig`, `library` and `setup` are listed to the model.
- An explicit mention still loads a hidden skill in full. Codex matches a plugin skill only by its qualified name, such as `$dig:reddit`, so the skills suggest that form.
- `setup` is the manifest's `extensions.com.openai.onboardingSkill`. It reads `settings.read` and `source_info`, asks which sources to enable, changes only the fields the user chose through `settings.update`, and explains each remaining step. It never handles a key and runs the Papers bridge only on the user's yes.

The **56 local provider tools** use the shared cancellation, raw capture and reported-cost boundary. The native boundary adds a required absolute `project` and optional `dig`, validates them before retrieval, and strips them before calling the provider implementation; the call's receipt records the `dig`. Settings are read for every call; disabled tools disappear from discovery and refuse calls. Existing saved evidence remains readable when its source is disabled.

`papers_multi_search` reads each requested connector's health from the bridge's `source_status` (`ok`, `empty`, `partial` or `failed`); output without it, or with anything else for a requested connector (another word or a non-string such as `["empty"]`), is an error, because it cannot establish coverage or no matches. The call's status follows the DataForSEO rule below: every requested connector failed is `failed`, and its text then opens with an `ERROR:` line naming them before the bridge's output; every one empty is `empty`; any failed or partial connector makes the call `partial`; the rest is `success`.

### Model-facing results

- Every tool result carries its complete value once, in `structuredContent`, and a one-line human summary in `content`. Codex's code mode prints the whole result to the model, so a value repeated in both fields would be read twice. A host path that forwards only `structuredContent` still receives everything.
- A provider call's `structuredContent` is the provider's details plus `text` (the formatted results), `status`, `project`, optional `dig`, `call` (the retained receipt, or null) and `retentionError`. A failed call also repeats the first error line in `content` and sets `isError`.
- `open_library`, `open_trail`, `library_list`, `library_read`, `source_info`, `dig_start`, `research_save`, `dig_finish` and every provider tool declare an `outputSchema`, so code mode can type the result. `source_readiness` answers in plain text only; app-only tools have no schema.
- These are model-facing result shapes. They change no persisted record.

`source_info` returns catalog entries with enablement, tool names, method names, absolute packaged `skillPath`, helper designation, worker guidance, credential-name presence, provider-setting presence (`envSettings`) and prerequisite details. Presence is not credential validity or proof the service is available. It neither probes credentials nor launches setup. Each method's `workerDefault` is the suggested worker model and effort in effect (below, under `[workers]`), with a `basis` that says whether the user set it in Dig's settings; it is guidance, and the initiating thread may choose differently. Dig's built-in suggestions are Sol/medium for every method, X breadth Luna/high and X judge Astra/high. Model availability belongs to the host/account, not the plugin; Dig does not check a named model against the account.

### X

X has two independent ways in. `xsearch` asks xAI's Grok to search X and returns Grok's write-up with links to the posts it cites; `[x]` settings choose its model and depth. The nine X API tools read X's own API v2 at `api.x.com` and return the posts and accounts themselves, read-only. Most reads use an app-only Bearer Token from `X_BEARER_TOKEN`. An optional sign-in signs exactly four reads as the user's own account, the ones X serves only in user context: people search, Communities search, the account's bookmarks and its liked posts. Each request carries one credential, in its `Authorization` header only.

`xsearch` asks Grok to cite every post inline by its full link, because Grok sometimes cites by number instead (`[post:50]`, `[120]`) with no link in its text; in the runs observed, its annotations then listed posts without positions and the numbers did not index that list (the post described at `[post:50]` was entry 27 of it). When a write-up still has bracketed numbers in its prose, the result counts them and says they look like citations by number but have no link, that Dig does not resolve which post each means, and that the Sources list is numbered by Dig, not by Grok. Prose is decided by parsing the write-up as Markdown, so a link's label (`[1](url)`, Grok's `[[1]](url)`), a resolved reference and code are not counted; a counted number is `[post:N]` or one to three digits (so a year is not one), alone or in a list or range such as `[1, 2]`. A bare `[N]` in ordinary prose is ambiguous, which is why the note says the numbers look like citations rather than that they are. xAI offers no limit on how many searches a pass makes: `max_turns` is accepted and ignored for X Search (observed 2026-10-07), so a pass's depth sets Grok's reasoning effort and the skills limit how many passes run. The X skills find and read posts through X's API and use `xsearch` for what only Grok does: watching a post's video and reading its images (X's API returns media links and metadata such as alt text, duration and views, not what the media show, and nothing else in Dig watches video), searching by meaning, finding accounts from a description, and the shape of a discussion. X post runs it for a supplied post's video or images, or when its assignment asks for Grok's reading; what Grok says media show is reported as Grok's description.

- `x_post` reads 1–100 posts by link or id through the multi-post lookup, then on request each post's thread (the author's posts in its conversation), replies, quote posts and reposters. Conversation reads search `conversation_id:<root>`: recent search when the conversation's root post is under seven days old, otherwise full-archive search with a `start_time` at the root post's creation, read from its snowflake id (X's archive start, 2006-03-21, for an id from before snowflake ids), because full-archive search defaults to the last 30 days. When X has more of the thread or replies than one reading took, the result says coverage is incomplete, gives how many posts it read and the `x_search_posts` call that reads on: the same query, `end_time` one second after the oldest post read (X's `end_time` is exclusive and to the second), `limit` 500 and, after a full-archive read, `archive` and the same `start_time`; it warns that posts from the oldest post's second may repeat. A thread or reply read that the 50-page safety limit stops names the limit and the posts read, and makes the call `partial`. `x_search_posts` passes X search syntax through to recent or full-archive search and pages internally with `next_token` up to `limit` (500), keeping each page as its own response, and says whether it stopped at `limit` or at its 50-page safety limit (which makes the call `partial`). With `archive: true` and no `start_time`, `x_search_posts` and `x_count_posts` send `start_time` 2006-03-21T00:00:00Z, so the archive means the whole archive rather than X's 30-day default. `x_count_posts` returns X's per-minute, hour or day counts and total. `x_users` reads accounts by handle, or by people search signed in, optionally with each account's recent posts and mentions. `x_news` reads X News stories (summary, hook, contexts and clustered post ids). `x_explore` reads trends by WOEID, Spaces search, Communities search (signed in, or through TikHub without sign-in) or a List's posts, and refuses arguments that belong to another kind. X answers people search and Communities search with an app token alone with HTTP 403 "Unsupported Authentication", so neither is sent that way.
- Requests ask for the reference's public app-only field set: every post, user, media, poll and place field and expansion except user-context metrics, the authenticated user's relationship fields, Community Notes program fields, the promoted-only `scopes`, the deprecated `source`, and the user fields `parody`, `subscriber_count` and `verified_followers_count`, which X refuses an app-only token on account lookups. X's API reference (OpenAPI 2.170, as X's own XDK sends it) spells these `post.fields`, `note_post`, `referenced_posts`, `repost_count` and `includes.posts`; its data dictionary still shows `tweet.fields`, `note_tweet`, `referenced_tweets`, `retweet_count` and `includes.tweets`, so responses are read in either spelling. A post's text is its long-form `note_post` text when present, verbatim; an X Article's text fields are shown as X names them. A repost's reference type is `reposted` as X sends it, or `retweeted` as its reference spells it; its own text is X's shortened "RT @handle: …" copy, so when X expands the original, the original's full text follows the "Reposting" line, in lists too.
- Requests are never retried and never follow a redirect, whichever credential they carry. A 429 is reported with the reset time from `x-rate-limit-reset`, without waiting. Full-archive search allows one request per second per app, so every full-archive request in the server process waits on one shared gate, a little over a second after the previous one, across calls. Output past 60,000 characters is truncated with a pointer to the retained original, and the parsed response is redacted before it is formatted.
- **Sign-in.** The X app's Consumer Key and Secret and an Access Token and Secret for the user's own account (`X_CONSUMER_KEY`, `X_CONSUMER_SECRET`, `X_ACCESS_TOKEN`, `X_ACCESS_TOKEN_SECRET`, from the app's Keys and tokens page) sign a request with OAuth 1.0a HMAC-SHA1 as RFC 5849 and X's "Creating a signature" guide describe it: every query parameter and the `oauth_*` parameters (consumer key, a random nonce, `HMAC-SHA1`, the timestamp, the access token, version `1.0`) are percent-encoded per RFC 3986, sorted and joined; the base string is the method, the encoded URL without its query and the encoded parameter string; the key is the encoded consumer secret and token secret. The query is sent percent-encoded exactly as signed (a space as `%20`). Only people search (`x_users` with `query`), Communities search (`x_explore` kind `communities`), `x_bookmarks` (its bookmarks, folder list and folder) and `x_likes` are signed; every other request, including the post lookup that reads a folder's posts, uses the Bearer Token. A read that needs sign-in without all four names set fails before any request, naming the missing ones. The signed-in account's id, which the bookmark and like endpoints take, comes from `GET /2/users/me` once per access token per server process, held in memory only; its response is kept with the call that first asked, a lookup in flight is shared and a failed one is not kept. Signed-in reads act as that account and see what it can see, including its private bookmarks and likes.
- `x_bookmarks` reads the signed-in account's bookmarks newest first, paged with `pagination_token` up to `limit` (800), or one folder: the folder list resolves a name (case-insensitive, exact) or id, and the folder's ids (X returns ids only) are read through the multi-post lookup, 100 per request, in the folder's order. An unknown folder fails listing the folder names X returned; when the list carried a problem or came back as a full page of 100 without a next token, it fails saying the list was incomplete instead of claiming the folder does not exist, and a problem beside a list that did hold the folder makes the read `partial`, naming it. X documents paging for both folder endpoints but its responses carry no next token, so a folder read that stops at a page of 100 ids before `limit` says the folder may hold more and is `partial`. The folder's post lookup follows the lookup rules above: posts returned beside requested posts X names missing, protected or suspended, or leaves out without naming, are `partial`, listing each; none returned with every post answered is `empty`, a resource-only failed response included; an operational failure stays a failure with X's message. `x_likes` pages the liked posts the same way (X takes at least 5 per page). `match` keeps a post only when every one of its words matches at the start of a word, case-insensitively (after the start of the text or a character that is not a Unicode letter or digit, so `ai` matches "AI", "AI's" and "#AI" but not "brainstorm", and `agent` matches "agents"), in the post's text or long-form text, its author's handle or name, its links' expanded addresses, or the text of a post it quotes or reposts; X has no search inside bookmarks or likes, so the filter runs on what was read and the result gives both counts. None read or none matching is `empty`, saying which; a later page or lookup failing beside posts read, or the page safety limit, is `partial`.
- `x_community` reads one Community by id or link: its details from X's Community lookup with the Bearer Token (X naming the Community missing, protected or suspended answers the call, and it is not read elsewhere), or from TikHub's `fetch_community_info` without one, whose `status` field is TikHub's join status and is not shown; and up to `posts` (500) of its posts from TikHub's `fetch_community_timeline`, paged with its cursor until enough, no cursor, no new post or a 30-page safety limit, each page kept as its own response and each post shown with its exact text, author, time, nonzero counts and link, the section labelled via TikHub. Stopping at the safety limit before `posts` names the limit and the posts read and makes the call `partial`; TikHub's Communities search pager has the same limit and rule. `sort: recent` asks for TikHub's Recency ranking, which is not strictly by time (one live page mixed posts from three days out of order), so the posts read are shown newest first by their own time and the result says a newer post may sit on a later page; `relevant` asks for its Relevance ranking and keeps TikHub's order. Without `TIKHUB_API_KEY` and with posts asked for, the details come back with a failure naming it (`partial`). Members are not read. A post in a Community, in full and in lists, and each Community a search finds, shows the Community's link `https://x.com/i/communities/<id>`.
- Every response's problems are classified where it arrives, in two groups kept apart. X's problems come as a failed response's body or as `errors` beside a 2xx response's `data`. A resource problem says a post, account or other resource is missing (`resource-not-found`), protected (`not-authorized-for-resource`) or suspended (`resource-unavailable`); an untyped problem with a `resource_type` and an identity (`resource_id` or `value`) is one too, unless it gives a status of 500 or more, which makes it an operational failure. Every other problem is a failure X reports: it fails a response that carries no data, and makes a response that carries data `partial`, naming it.
- A lookup by id or handle (the `x_post` post lookup, `x_users` by handles, an `x_news` story by id and a List's posts) takes a requested item that a resource problem names, in a 2xx or a failed response, as that item's answer, with X's reason. Every other read (search and count pages, quote posts, reposters, an account's posts and mentions, people and News search, trends, Spaces, Communities) treats a response with no data beside any problem, resource problem or not, as a failed read named in X's words, never as zero results; beside data, resource problems are about expansions such as a referenced post or an author, and are left out. A List that X returns with no posts and no problem is an empty List. A search or count page that fails or carries a failure ends the reading with it named, never taken for the last page.
- Outcome: every requested post or account returned is `success`; some returned and others not, or a failure X reported beside the data, is `partial`, naming each missing item with X's reason or saying X named none; none returned is `empty` only when X answered for every requested item, and `failed` when any has neither data nor an answer. An HTTP, authentication, credit, rate-limit or network failure, or a failure X reports without data, is `failed`. A search or count with no matches is `empty`; a later page failing, or carrying a failure, after earlier pages returned is `partial`, and so is a requested thread, reply, quote, reposter, post or mention read that failed, carried a failure or stopped at the page safety limit beside returned posts.
- When `x_post` names exactly one post and `X_BEARER_TOKEN` is not set, or the post lookup fails with an authentication (401/403), credit (402), rate-limit (429) or server (5xx, or an `internal-error` problem without data) failure or cannot be reached, the post is read through TikHub's `fetch_tweet_detail` with `TIKHUB_API_KEY` (and `TIKHUB_BASE_URL`), once and without following a redirect (a 3xx is retained and fails the fallback), and the result and its retained response are labelled "via TikHub". The fallback counts as reading the post only when TikHub returns that post's own id with its text or media. A thread, replies, quotes or reposters requested with it are named as needing the X API, which makes the call `partial`. Any resource problem in the lookup's failure, or in a 2xx lookup without data, vetoes the fallback, whatever it names and whatever else X reported: the call is `empty` when the resource problems answer for every requested post, and otherwise `failed` with X's message and the resource problems quoted, saying X refused or withheld the post, so it was not read elsewhere. Several posts with an X failure fail with X's error.
- Communities search without sign-in is read through TikHub's `fetch_search_communities` (`keyword`, paged with `next_cursor` until `limit` or no new Community), labelled via TikHub; with neither sign-in nor `TIKHUB_API_KEY` it fails before any request, naming both. Every TikHub read follows the fallback's request rules: one request per page, never retried or redirected, kept under a "via TikHub" label.
- X reports no per-call charge, so every X API call, and every TikHub read, records `cost: null` with no `knownCost`; results state how many posts and accounts came back, never a price. X prices reads of the signed-in account's own bookmarks and liked posts as Owned Reads ($0.001 per resource, X changelog of 2026-04-16); a folder's posts go through the ordinary post lookup.

### Facebook

Facebook and Facebook ads are separate report sources sharing `SCRAPECREATORS_API_KEY`, not a Facebook account or login. `scrapecreators_facebook` reads public profiles, profile posts/reels/photos, native video search, individual posts, transcripts, comments/replies and group information/posts. `scrapecreators_facebook_events` reads a page's events, event search, a city's event listing and individual event details. `facebook_ad_library` searches ads or advertiser pages, reads an advertiser's ads, individual ad details and ad transcripts. Ad Library evidence is a transparency record, not a performance dashboard; returned regional or political delivery disclosures retain their source-specific units.

Each call makes one request, never retries or follows a redirect, and retains its response through the existing boundary. List calls expose the provider's continuation, not an automatic crawl. Reels and photos require both `cursor` and `next_page_id`; Ad Library search and company continuations send the same parameters by POST because cursors can outgrow a URL. Facebook documents three posts per profile/group page and up to ten reels per page. Native video search is not general Facebook text-post search. These scopes and page limits are not evidence that no other content exists.

The tools forward `cache_max_age` only to endpoints that document it. Cost is the returned `credits_charged` through the existing ScrapeCreators billing reader; absent pricing stays unknown. A profile's private or age gate is explicit: limited public fields are `partial`, a gate with no fields is `failed`, and a provider-reported missing profile is `empty`. Real empty arrays or unavailable transcripts are distinct from malformed responses and request failures. Mixed readable and unreadable list entries are `partial`. Output retains text, links and pagination before a 60,000-character bound; complete originals remain available when raw retention succeeded.

Media URLs and metadata are not visual analysis. Ordinary post transcripts are documented for videos under two minutes. Ad transcripts may come from Facebook captions or ScrapeCreators' transcription of the public video; the response does not identify which. The skills preserve that distinction and do not infer video contents or ad performance. Facebook uses the reader's existing original-JSON view rather than a separate evidence projection.

### DataForSEO

DataForSEO is an ordinary local source over its v3 REST API, with HTTP Basic authentication from `DATAFORSEO_USERNAME` (the API login) and `DATAFORSEO_PASSWORD` (the API password, not the dashboard password). The password and the encoded Basic credential are redacted secrets; the login is not. Request headers are never retained. The provider redacts the parsed response before formatting it, because the boundary's exact-match redaction cannot find a credential after JSON escaping or truncation has changed its text.

- The three documentation tools read DataForSEO's public docs site: `dataforseo_docs_sections` and `dataforseo_docs_index` parse its `llms.txt` endpoint index (sections, heading trail, page path, summary), and `dataforseo_docs_read` pages one page's Markdown twin by character offset. They record no charge. The site redirects pages to trailing-slash URLs; those redirects are followed by hand only within `docs.dataforseo.com`, at most three hops.
- `dataforseo_request` sends one request to `api.dataforseo.com/v3/<path>`, or to the free `sandbox.dataforseo.com` with `sandbox: true`, which returns dummy data and is labelled as such. Paths are validated segment by segment; `.ai` paths are refused because only the full response reports the call's cost. Requests are never retried and never follow a redirect: a 3xx is retained and reported as a failure with unknown cost, so a request cannot leave the DataForSEO hosts or hide an attempt from billing.
- Its cost is the response envelope's top-level `cost` in USD; a response without a usable `cost` is unknown, never zero. The output lists the top-level and per-task status, cost and result count, then the tasks' request echo and results with null and empty fields removed, truncated past 60,000 characters with a pointer to the retained original.
- Outcome follows DataForSEO's Appendix of status codes. An envelope status other than 20000/20100 is `failed`. Per task: 20000 with results, or a task accepted without results yet (20100 Task Created, 40601 Task Handed, 40602 Task In Queue), is success; 20000 without results and 40102 No Search Results are empty; 40106 (partial results, uncharged missing pages) and any other code count against the call. All tasks failing is `failed`; any failing or partial task makes the call `partial`; otherwise any results or accepted tasks make it `success`, and the rest is `empty`.

## One inspectable settings authority

Codex's native controls and Dig's Sources and Settings pages call the same `settings.read` / `settings.update` backend, editing `<state>/config.toml`. Codex draws its own page from the settings schema and layout as three flat groups, Library, Source workers and Sources; a plugin cannot restyle or nest them, so the richer presentation lives in Dig's view. Both tools stay visible to the model on purpose, so onboarding and orchestrating conversations can apply choices the user states in chat; the skills tell the model to change only what the user chose. The Sources group of Codex's plugin settings page also carries a **Check source readiness** button, which runs `source_readiness` and shows its plain-text summary.

```toml
library = "/absolute/path/to/research"
keep_raw = true

[sources]
enabled = ["hackernews"]

[x]
model = "grok-4.7"
depth = "standard"
web_search = false
code_execution = false

# Only where a suggestion differs from what the method would otherwise get:
[workers.default]
model = "gpt-7-sol"

[workers.x-judge]
effort = "xhigh"
```

- Missing values use these defaults; existing 0.1.x files need no migration. `sources.enabled` may be empty or contain unique catalog ids. Unknown fields and invalid values fail before replacing the file.
- Native boolean fields such as `tikhub_reddit_enabled` are views of membership in `sources.enabled`, not separately persisted values. The `x_*` controls map to `[x]`; they configure `xsearch`'s xAI retrieval, not the X API tools or the Codex worker. `[x] depth` is the starting depth: the X skills leave `depth` out of ordinary passes so it applies, and pass `max` only for a nuanced, disputed or synthesis pass (judge) or a final sweep (breadth), or `quick` for an explicit existence check. The judge runs at most three `xsearch` passes and breadth at most four, each passing `max` at most once, and both find posts through X's search: a Grok pass pays for every post it fetches while its write-up links only a fraction of them. A `max` or `ultra` starting depth is the user's choice and applies to every pass; only the pass limits then apply. `[x] web_search` applies unless an assignment explicitly asks to add or exclude web results for a pass.
- **Suggested source workers (`[workers]`).** Worker suggestions are guidance for the initiating thread, never enforced pins; `[workers]` lets the user change them without a Dig release. Tables are `default` and any of the 24 catalog method names (`hackernews`, `x-judge`, `youtube-summarizer` and so on). Each holds optional `model` (a nonempty name, trimmed, never checked against the account) and `effort` (one of Codex 0.160's reasoning effort names: `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, `ultra`); any other table or key fails like any unknown field. Each field resolves separately: the method's own table, else Dig's built-in suggestion for that method (only X judge and X breadth have one), else `[workers.default]`, else Dig's built-in default. So the X methods keep their own suggestions when the Dig-wide one changes. The only reader is `source_info`'s `workerDefault`; nothing spawns or pins a worker.
- Worker settings fields are flat views of `[workers]`: `worker_model`/`worker_effort` for `default`, and `<method with underscores>_worker_model`/`_worker_effort` per method (`x_judge_worker_effort`). `settings.read` reports each field's effective value. A `settings.update` of a worker field stores it only when it differs from what that table would inherit, and removes the field (and an emptied table) otherwise, so echoing a shown value stores nothing and a method keeps following the Dig-wide suggestion until it is given its own; a value written by hand is kept as written until that field is next updated. `[workers]` is written only when it holds something. Dig's controls send one field per update. If a host sent a whole form in one update, an unchanged per-method echo beside a Dig-wide change would be stored as that method's own suggestion; whether Codex's own settings page sends only changed fields is not verified.
- Updates preserve omitted values, serialize within the server and atomically replace the file. Each control on Dig's pages saves only its own field when it changes (a switch at once, a text, number or choice field when committed), one `settings.update` at a time in order; the values that call returns are what the control then shows, and a refused save restores the last saved value and names the error beside the control. A settling save never repaints what the user changed after it began, a draft typed into a text or number field is left until it is committed, and while a control's save is running, a background refresh leaves that control to the save's result. Deliberately editing the same field in two surfaces is later-save-wins. Hand-edited source selection is synchronized with discovery by a file watcher.
- Changing `library` selects a directory; it never moves research. Neither the save nor any read creates the directory; a research write does, such as `dig_start`, a provider call's receipt or `research_save`. A mistyped path therefore stays absent instead of becoming an empty library, and `library_snapshot`'s `libraryFolder` (`folder`, `missing` or `not-folder`) lets the Settings page say so under the field; it is part of `library_revision`'s fingerprint, so creating the folder outside Dig clears the note. A missing library lists as empty. The browser preview is read-only. There is no second UI preference store.

### Credentials and optional executables

Dig takes credentials only from native `<state>/keys.env`; a key in the user's environment is not assumed to be meant for Dig. The file uses the existing `NAME=value` convention for catalog environment names; the first nonempty assignment of a name wins, and an empty `NAME=` is a placeholder. Credentials are the secret-shaped names (`…_KEY`, `…_TOKEN`, `…_SECRET`, `…_PASSWORD`) plus logins a source requires, such as `DATAFORSEO_USERNAME`. On its first load the server sets aside whatever the environment Codex started it with holds for catalog names: those credentials are not used, stay registered for redaction, and are reachable only by the per-source copy below. For the other catalog names (base URLs, timeouts, the Unpaywall contact email) a `keys.env` value wins and the starting environment's value is the fallback. The server watches `keys.env` and reapplies it whole when it changes; an unreadable file leaves the previous values in effect. `source_info` and the Sources page disclose names, presence and how the environment compares (`environment`: `absent`, `unused`, `same` or `different`), never values. Do not put secrets in chat, provider arguments, manifests or version control.

Readiness counts a source's catalog `keys`: each entry is one credential the source uses (an inner list names aliases, any one of which is enough). With every entry set the source is ready, with some it is partly ready, and with none it needs setup; credential names in its `env` but not in `keys` are optional and never change readiness. GitHub, Papers, YouTube and Commerce add their own rules for logins, bridges, executables and their two providers. X lists `XAI_API_KEY` (for `xsearch`) and `X_BEARER_TOKEN` (for the X API tools), so it is ready with both, partly ready with either one, and needs setup with neither. Optional for X, in its `env` only: the four sign-in names (`X_CONSUMER_KEY`, `X_CONSUMER_SECRET`, `X_ACCESS_TOKEN`, `X_ACCESS_TOKEN_SECRET`), which are secret-shaped and so redacted and registered like any key, and `TIKHUB_API_KEY`, used by `x_post`'s single-post fallback, Communities search without sign-in and a Community's details and posts. A tool whose own key is missing fails with a message naming it.

A catalog entry's `envSettings` names the non-credential settings worth showing the user, with a label and purpose; today only Papers has one, `PAPER_SEARCH_MCP_UNPAYWALL_EMAIL`, without which the Papers bridge skips its `unpaywall` connector. `source_info` reports each as `available` (set in Dig's environment: `keys.env`, else Codex's) or, for Papers, `bridge` (set only in the bridge's own `.env`, where the bridge setup's `--email` writes it and which the bridge reads when Dig's environment lacks the name), never the value. A contact email is not a credential, but it stays in `keys.env` rather than `config.toml` because `settings.read` is model-visible. The bridge echoes the address in its diagnostics (Unpaywall's rejected-email warning names it; an HTTP error quotes the request URL), so the Papers bridge tools scrub every address the bridge could be using, from either place and under either of the bridge's names (`PAPER_SEARCH_MCP_UNPAYWALL_EMAIL` or plain `UNPAYWALL_EMAIL`), as written and as URL-encoded, from both of its output streams before anything is kept, truncated or returned. Only a value containing `@` is scrubbed, so a placeholder such as `none` cannot blank ordinary words in evidence. The address is not added to the general credential redaction, which would corrupt evidence that legitimately contains it.

There is deliberately no credential field. Codex's native settings schema has no password format, and `settings.read`/`settings.update` are model-visible tools, so a value entered there would pass through the conversation. Instead, each source's card on Dig's Sources page offers two app-only actions in the Keys section of its Setup details, and the top of the page offers the first for every source:

- **Edit keys.env** calls `prepare_keys_file`: it creates the file with mode 600 if it is missing and appends, under a comment naming the source(s) and guidance, an empty `NAME=` line for each credential name the file does not already assign (commented assignments count), then one for each of the source's `envSettings`, each under a comment with its label and purpose, so the file shows everything Dig can use. It never changes existing lines or file mode and returns only the path, the names it added and whether it created the file. The view then asks Codex to open the file through the OpenAI `files.open` extension; without that capability it shows the path.
- **Use existing key** (labelled **Update key from env** when `keys.env` holds a different value) calls `use_environment_keys` for one source: it copies each of that source's credentials whose environment value is `unused` or `different` into `keys.env`, replacing the name's first active assignment or appending it under the source's comment, writes the file atomically at mode 600, applies it at once, and returns only the names copied. There is no blanket copy across sources.

Credential presence, environment comparison and whether the Papers bridge's own `.env` holds each Papers setting are part of the view's revision, so readiness on an open Sources page refreshes in place after a save to either file, keeping keyboard focus and a field being typed in.

The shared boundary redacts known credential values from provider output, grouped questions before deriving folder names, saved reports/answers, receipt arguments and retained bodies. Known values are the current secret-shaped catalog values plus every one the server has loaded from `keys.env` or set aside from its starting environment since it started, so a key rotated or removed while a request that used it is still running stays redacted from that request's result and retained responses. Each value is also redacted in the two spellings URL encoding gives it (`encodeURIComponent` and form encoding), because Scrape.do and Just One take their token as a query parameter and a response that echoes the request URL would otherwise carry it past an exact match. Receipt arguments also omit credential-shaped field names. A retrieval whose receipt cannot be saved returns `retentionError` alongside its provider result; it is not presented as retained evidence. Raw files exist only when retention is enabled and a response was captured.

YouTube discovers an explicitly installed `yt-dlp` on PATH or conventional install paths; it never installs it or reads browser cookies. Current yt-dlp needs a JavaScript runtime (Deno by default, or Node 22+) for full YouTube support, and drops caption tracks that YouTube gates behind a proof-of-origin token unless a token provider plugin is installed; Dig's readiness check does not look for either. Transcripts are write-once shared files in `<library>/youtube-transcripts/`. A transcript is YouTube's English automatic captions as plain text, without the caption file's header (`WEBVTT` and the lines up to the first blank one, where YouTube puts `Kind:` and `Language:`) and dropping only the captions' rolling overlap (a line equal to the one before it), so a sentence said again later stays. A video that already has a transcript file reuses it rather than fetching again, so transcripts saved before 0.2.20, which dropped every repeated line and began with that header, stay as they were. The helper's sibling `-summary.md` uses the host's file writer and remains subject to its sandbox and approval policy.

The optional Papers setup is `plugin/bridges/papers/setup.mjs`. It installs a pinned, patched `openags/paper-search-mcp` checkout beneath `<state>/tools/paper-search-mcp`, with its own Python environment and `.env`; it never uses `~/.omp/tools` or the old edition's configuration. Runtime uses `uv run --no-sync`, not implicit installation. Setup's live research smoke is opt-in, and no email or key is inferred/copied. The maintained upstream patch keeps its per-user NCBI lock in `~/.cache/paper-search-mcp`; it is coordination data, not a credential or research-library dependency.

`source_info` reports two local prerequisites for Papers: **Papers bridge and uv** (installed bridge interpreter and `uv` on PATH), which decides its readiness, and **git**, which setup needs to clone the bridge. Searches never run git, so a missing git does not change readiness; it only means the bridge cannot be installed or updated here.

Setup recognizes only the exact current or previously shipped patch at the pinned upstream commit before replacing it; staged, unknown tracked or untracked changes are refused without removing the installed patch. The previous patch is packaged only for this upgrade check. Run setup while the bridge is idle. An existing Python environment is reused without dependency synchronization.

The build generates `.mcp.json` environment forwarding from the catalog and includes a 30-second startup and 600-second tool timeout. Host permissions remain independent; no approval policy is changed by installation.

## Research files and immutable writes

Research files use the vocabulary of the original Dig edition. A receipt names the dig its call named; there are no worker-parent or model-provenance fields.

```text
<library>/<project-folder>/
  digs/<dig-id>/
    dig.md
    <method>.md
    <method>-2.md
    answer.md                 # optional parent answer for composed digs
  sessions/<session-id>/
    calls.jsonl
    raw/<call-id>.json
<library>/papers/             # downloaded PDFs shared by Papers methods
<library>/youtube-transcripts/ # transcripts and optional helper summaries
```

- Project identity is the caller's explicit absolute existing directory, not plugin cwd. Its folder uses the basename slug and six characters of its absolute-path SHA-256.
- `dig_start` is an optional initiating-thread grouping helper. It writes `dig.md` with `dig`, `question`, `project`, `mode: composed`, `started_at`, `session`, optional `planned` method names and optional `refreshes` pointing to an existing dig in that project. IDs use the native UTC timestamp and question slug, with collision suffixes.
- `research_save` without `dig` requires `question` and creates `mode: single`. The report carries `title`, `dig`, `source`, `agent` (method), optional `topic`/`topic_volatility`, `generated_at`, `project`, `session`, and optional same-dig `supersedes`. Reports are numbered instead of overwritten. X reports require the actual method (`x-judge`, `x-breadth` or `x-post`).
- Reports begin with their method's fenced `source_card`, then keep `## Summary`, `## Evidence Highlights`, `## Needs Follow-Up` and `## Negative Evidence (when relevant)` in the body. The save checks this structure, not the truth of the report. The UI labels the source card as the source worker's own assessment.
- `dig_finish` writes an initiating-thread `answer.md` once for a composed dig, with `dig`, `finished_at`, `status` and existing `reports` filenames. `status` says whether the answer settles the question: `answered`, `partly-answered` (part of the question is still open) or `unanswered`. A failed search, a source that was down or a worker that stopped is a limit the answer states; it does not make an answered question partly answered. An answered dig names at least one report. Single-source research does not require or receive an invented composed answer. A status Dig does not write shows only as **answer saved**.
- Every local provider call appends a receipt: `id`, `at`, `ms`, `tool`, `source`, `status`, optional `dig` (the dig id the call named; from 0.2.20), provider `args`, `cost`, optional `knownCost`, optional response `attempts`, optional session-relative `raw`, and optional failure `error`. The host's `_meta.callId` supplies the id when present. `cost: []` records no provider charge; `cost: null` means the total is unknown; a nonempty array is a complete provider-reported amount in its original units. No host model cost is inferred.
- Raw files contain `tool`, `at`, and `responses` with `label`, `status` and returned `body`. The only optional response-header evidence is `headers: {"scrape.do-request-cost": "<exact returned string>"}`; no request headers, cookies, account balances or general response headers are retained. Normal secret redaction still applies. Raw files and receipts are write-once; existing files remain unchanged.

### Provider-reported usage costs

Cost describes the provider's reported usage, not a reconciled cash invoice. An OpenAlex usage cost can be funded by its free daily allowance. Estimates, balance deltas and model-written source-card cost claims are never added to receipt totals.

- `knownCost` is valid only alongside `cost: null`. When present it is a nonempty array of positive finite `{amount, unit}` values, aggregated once per exact nonblank unit. It preserves a reported subtotal while the complete total remains unknown. Zero subtotal entries are omitted, and totals consume either `cost` or `knownCost`, never both.
- The execution boundary accumulates billing evidence as responses arrive, independently of retrieval outcome. An unpriced response makes the tool call incompletely priced; an exception or observed cancellation on a metered call also leaves its total unknown while retaining the positive subtotal. A normal failed result can still have a complete reported cost. Missing responses do not establish that no request was charged. Existing explicit no-charge source policies remain separate.
- Numeric billing values must be finite and nonnegative. Invalid billing is unknown, not zero. Header-bearing responses are captured once before an abort propagates, even when body reading is interrupted. Normalized costs survive server restart and `keep_raw = false`; original billing evidence is available only when raw retention was enabled.
- Exa reads `costDollars.total`; Perplexity Agent reads `usage.cost.total_cost` and its currency; `xsearch` converts xAI's USD ticks to USD. ScrapeCreators retains its established `credits` unit, displayed as **ScrapeCreators credits**. Commerce reads Scrape.do's response header as **Scrape.do credits**. Distinct credit systems are never merged or converted to dollars.
- Direct OpenAlex search reads `meta.cost_usd`; an otherwise unpriced documented 4xx/5xx records no charge, while an unpriced 2xx or transport failure stays unknown. Federated Papers search prices only its requested OpenAlex-backed connectors (`openalex`, `ssrn`): the bridge emits optional `billing` with one `{http_status: number | null, cost_usd: number | null}` entry per requested connector. Status is 100–599 or null without a response; cost is finite and nonnegative or null when unusable. With no such connector, `billing` is absent. The adapter prefers usable USD, otherwise the existing per-request `rate_limits[source]["credits-used"]` as **OpenAlex credits**, never both. Missing or malformed entries do not establish zero. The other 17 federated connectors retain their existing no-charge policy; this correction is not a fresh pricing audit of them.
- TikHub has no established per-request amount in the checked response contract. Nexscope's `costToken` is token consumption, not documented charged credits; its actual charged-credit history is a separate account API. The X API draws pay-per-use credits from the developer account and reports no charge on its responses, so the X API tools declare no billing reader and every call records `cost: null`, signed in or not, as do their TikHub reads. New calls without authoritative per-request pricing remain unknown. Account-wide reconciliation is not performed.
- Old receipts are not rewritten or backfilled. Historical federated Papers receipts may incorrectly record no charge; receipts have no producer version with which to identify that subset reliably. Federated Papers receipts saved before 0.2.15 also record `success` whatever their connectors' health, including a search whose every connector failed. **Recorded no provider charge** reports the saved claim, not verified invoice history.

The source selection determines the federated Papers call's policy before execution. A selection containing only the other 17 connectors keeps the explicit no-charge policy on every exit, including setup failure and cancellation. A selection containing OpenAlex or SSRN—including the default all-source selection—uses metered finalization, so missing output is unknown and cancellation preserves only the observed subtotal.

### Conversation identity and attribution limits

`session` is the filesystem-safe calling Codex `_meta.threadId`, including a worker's own thread. Missing identity is `session-unavailable`; it is never guessed from recent work.

A receipt that names its `dig` belongs to that dig, whichever conversation made the call, so its cost counts toward the dig even when no report is ever saved with it, as when a worker stops before saving. A receipt naming a dig that is no longer in the library stays live activity.

A receipt without `dig` (every receipt before 0.2.20, and calls made without one, such as a single-source worker's before its save creates the dig) follows the session rule. Within a session, it belongs to the dig of the first later report save or composed-dig finish: a report's dig takes it; a composed dig's finish takes it only when the call started at or after that dig's start. Unfinished composed digs have open endpoints; the newest-started dig wins a tied open endpoint. Unclaimed completed retrievals are **live activity**, not proof of a running worker. Old receipts are not rewritten, so a stopped worker's calls saved before 0.2.20 stay live activity rather than counting toward the dig they served.

Within its dig, either kind of call is claimed by that dig's first later save in the call's own session that accounts for it: a report of the call's own source, else the dig's finish when that session started the dig (for a call without `dig`, only when it started at or after the dig's start). A report therefore never claims another source's calls, such as a search the parent made before saving a report of a different source. A call with no such save, such as a stopped worker's, one from a source no report of its session covers, or one made after the answer, is in the dig as **not in a saved report or answer**. Which report claims a call never changes which dig it belongs to.

The session rule has limits: overlapping questions in one thread, equal timestamps, and clients sharing the unavailable-session bucket can be ambiguous. A direct single-source worker's dig belongs to that worker, not automatically to its parent. The Research trail shows digs started in the current conversation; use parent-created grouping when that association is wanted, or browse the Library. No persisted parent-worker relationship is invented.

## Reader and conversation-side view

- `library_list` provides bounded agent discovery by project, source and query, with offset/limit (20 default, 100 maximum). Queries match titles and the first 280 characters of each report's Summary, not full-text evidence. `library_snapshot` is the app-only full view. Sources, methods, summaries and correction/refresh labels are derived from files, not a second stored catalog.
- `library_read` accepts a library-relative reference or an absolute path confined to the active library. It pages reports, answers, transcripts, receipts and raw JSON; follow `nextOffset` until null. Reads and library record writes reject path escapes and out-of-library symlinks. Reads return only Dig's research files: `<project>/digs/<dig>/*.md`, `<project>/sessions/<session>/calls.jsonl`, `<project>/sessions/<session>/raw/*.json` and `youtube-transcripts/*.md`. Any other Markdown or JSON under the library is refused, because the library folder is a model-visible setting: a read that took any file under it would let a model pointed at another folder read that folder's files. The `dig://library/` resource and the saved-research card read through the same rule.
- `open_library` is the global entrypoint; `open_trail` is the separate conversation-side **Research trail** entrypoint. Both use the library view, `ui://dig/library/v<version>.html`, in fullscreen host display mode with no external resource/connect domains, and carry a monochrome shovel glyph (`openai/iconStyle: monochrome`; the server declares the same glyph as its icon). Their results name only the requested view, the calling thread and the library path; the view loads its own data through app-only `library_snapshot`, so the model's context does not grow with the library. A missing thread id leaves the panel explicitly unidentified.
- The main Dig skill and server instructions ask the initiating thread to call `open_trail` once when live research starts, not from workers or on every source call. This is model-mediated opening with a host display preference, not a guaranteed on-use hook. Host refusal or an unavailable UI does not block authorized research. The view shows saved digs/reports and completed retrievals; it does not invent worker-start or percentage-complete state.
- While visible, the UI polls a cheap filename/size/mtime/settings/credential- and setting-presence revision every two seconds. Updated cards, tabs and the Retrievals summary do not replace the open document, native text selection or keyboard focus. New files are announced rather than opened.
- **Retrievals, at the top of an open dig** (`src/ui/retrievals.mjs`), sit between the dig's title and its file tabs, in the library and the conversation-side panel alike; the document beneath takes the full width. Computed in the view from the dig's receipts, they reuse Usage's parts (below): four figures (retrievals, sources, failed or stopped, provider cost with the incompletely priced count), one bar per source split by outcome with its cost under it, the outcome legend and the cost scope and caveat. Then the **All N retrievals** fold, closed by default and built once per dig so a live update leaves it open or closed, lists every call grouped by what saved it: each report in save order, with its own source-card status as a tag, then the conversation that started the dig, then calls not in a saved report or answer (its summary counts these). Each group gives its count and cost; failed or stopped calls lead it. Each call is one entry: its outcome tag, what it did, its error when it failed, source, time, duration, cost and the button that opens its original response.
- **Figures, at the top of the conversation panel** (`showPanelFigures` in `src/app.mjs`), above its dig cards: the same four figures as an open dig's Retrievals (retrievals with how many returned results, sources with how many reports were saved, failed or stopped, provider cost with the incompletely priced count), two by two, with the cost scope and caveat and no charts. They count exactly the calls the conversation's cost counts (below). Unclaimed calls from workers and other conversations are not counted, because a call that names no dig cannot be attributed until a report claims it; when there are any, a line says how many are not included. A conversation with no calls and no reports shows no figures.
- Dig cards, the open dig and the current conversation show provider-reported totals or subtotals with the count of incompletely priced **tool calls**, not an invented HTTP-request count. Conversation totals include its digs' attributed calls and its own unclaimed calls, excluding other conversations' and workers' unclaimed calls. Zero retained calls produce no cost claim. Every summary carries the retained-calls-only scope, Codex model-cost exclusion and invoice caveat; the Library's dig cards show only their totals, and Usage above them states that scope and caveat once for the page.
- Markdown is tokenized and rendered through DOM allowlists. Raw HTML remains literal text; images do not load. Only HTTP(S) links navigate. Original JSON is always reachable and opens when a useful source preview is unavailable or fails to render; a preview failure is labeled explicitly, never treated as negative source evidence.
- The build embeds the installed `@openai/mcp-extensions/app/styles.css` unchanged. Controls use its shared classes; layout and typography follow the first-party plugin conventions. Host color/font variables govern appearance. The muted role is derived from the host foreground/background to preserve readable contrast; neutral fallback focus and checked controls remain distinct. There is no separate branded background palette, oversized hero or duplicate document title.
- File paths remain available under **File details** and **Library location** rather than occupying the primary reading surface. Status is a lowercase tag (`src/status.mjs`): a word on a borderless patterned fill, so no state rests on red/green meaning. A dig shows its answer's status (**answered**, **partly answered**, **not answered**), else **answer saved**, **report saved** or **started**; a report its source card's run status as written (**complete**, **partial**, **failed**); a call its outcome (**results**, **some results**, **no results**, **failed**, **stopped**, **skipped**). Solid fills mean done, light stripes partly, light orange stripes not done, dots nothing yet; the stripes stay faint so the word reads first. Browser preview is read-only; it cannot save settings.
- **Sources, Settings and About.** Besides the Library (and the conversation-side trail), the view has three pages. **Sources** renders one card per catalog source in `SOURCE_GROUPS` order (`src/providers/modules.ts`), grouped by what a source researches rather than by provider: readers look for Reddit, not ScrapeCreators, and several sources use two providers. Each card takes its copy from the catalog entry's `about`, `providers` (named with links), `billing` and optional `logo`, and shows its switch and readiness; a table of contents at the top jumps to a card and focuses its heading. The readiness line stays in sight; a missing-key sentence ends by pointing at Setup details. The rest of the card's setup sits in its **Setup details** fold, closed by default: a native `<details>` whose summary `fold` (`src/ui/dom.mjs`) styles as a button, with a border, a hover fill, the title, a gist of what it holds ("Keys and suggested worker", "Local tools") and a chevron that turns when it opens, so the browser supplies the keyboard toggle and the expanded state. Inside are Keys (each credential and `envSettings` name after a **set**, **missing** or **not set** label; the list has two columns, the first as wide as its widest label, so the names start at one edge, a long name wraps in its own column and its details sit under it; **Edit keys.env** beside the title; which other sources the same credential covers; and the environment-copy button with its sentence kept visible because it changes keys.env), On this computer (each prerequisite after an **installed** or **not installed** label), then Research method(s). Every status label on the page (readiness, presence, installed) is a lowercase word with no border, so it does not read as a button beside the bordered buttons and fold bars; its word carries the meaning and its fill repeats it: a solid tint for set or ready, grey stripes for partly, orange stripes for missing or needs setup, dots and muted text for not set or off. The gist names keys only when the source has credential or `envSettings` names, so a keyless source's guidance line is not called keys, and the fold is hidden when it would hold nothing. Text every card would repeat (what Edit keys.env does; what a worker suggestion means) sits in a note behind an (i) button beside the section title: hovering opens it, a click or Enter pins it, Escape closes it and returns focus to the button, a click elsewhere or closing the fold around it closes it, and only one is open at a time. A settings key belongs to the source with the longest matching id prefix, so `tiktok_ads_enabled` belongs to TikTok ads and the `x_*` fields sit in the X card. A method's worker fields (`*_worker_model`, `*_worker_effort`) sit under Research method(s) rather than among the card's own settings; that section comes from the catalog's methods, so it shows even when `source_info` is unavailable. Setup details and its Research method(s) section are built once per card and never moved, and a readiness refresh rebuilds only the Keys and On this computer sections and the gist (closing a note open inside them), so an open fold stays open and keeps keyboard focus on its summary: a browser commits a draft in a field taken off the page as a change, so moving the worker fields would save a half-typed model name. **Settings** renders every field no source owns, grouped as the layout groups them (Library, Source workers), so a future Dig-wide field appears there without view changes. **About Dig**, from the footer, shows the view's and the server's version, the library, settings and keys paths, the key, privacy and cost rules, and credits; Back returns to the page it came from, which keeps refreshing. Readiness, switches and the table of contents refresh in place on each revision change.
- **Usage, at the top of the Library** (`src/ui/usage.mjs`), above the search and the dig cards, is computed in the view from the snapshot it already holds: every retained call receipt, whether it is in a dig or still live, and each report's `generated_at` (carried as `at` in `reportDetails`, view data no record stores). A window of 7 days, 30 days or all time (since the first dated receipt or report) gives four figures (retrievals, reports saved, retrievals that failed or stopped, provider cost), retrievals per local day (per week past about two months) and retrievals per source, the six busiest shown and the rest behind a disclosure. Outcomes group receipt status: `success` and `partial` returned results, `empty` returned none, and `failed`, `cancelled` and `skipped` failed or stopped; each has a legend word and its own fill pattern. Cost uses `costSummary` per unit, never converted or added across units, with incompletely priced retrievals counted and the usual scope and invoice caveat. Bars are SVG sized from numbers, so the view needs no inline style. The window lasts while the view is open and is never saved. A library with no dated receipt or report in any window (a new installation, or digs started without a retrieval) shows **No usage yet** and what will be counted instead of empty figures; a window that is only quiet keeps its zeros and the window switch. The section is drawn while the Library shows, and stays empty until the first snapshot arrives so a library with research never flashes the empty state. Where the Library is 560px wide or less, as in the conversation panel, a container query keeps the window switch, the four figures (smaller, two by two) and the cost scope and caveat, and hides the two charts and their legend, so the dig cards start near the top.
- **Accounts and keys, at the top of Sources** (`src/ui/accounts.mjs`), is a titled section like the source groups: the title with **Edit keys.env** (every source's names) beside it, a sentence that keys live in keys.env outside the chat and that one key can serve several sources, the keys.env path, then the **Where to get each key** fold of the same kind as Setup details, closed by default, whose summary says how many of the catalog's accounts are set in keys.env and, when any are missing, how many local tools are not installed. The section shows when `source_info` gives a keys path or sources. The fold opens to one tile per provider account from the catalog's static `ACCOUNTS` (`src/providers/modules.ts`), because one key can serve several sources (one ScrapeCreators key covers eight, TikHub's four, one of them optionally). Each account carries its keys.env names (an inner list names aliases of one credential, as a source's `keys` does), optional names no source needs (the X API account's four sign-in names), listed after its own and never changing its state, the provider's own page for creating or finding the key (checked against the provider's documentation on 2026-10-05, the X API's on 2026-10-06), and a short billing line drawn from its sources' catalog copy and that documentation, adding no price. The view derives which sources an account serves, and whether each needs it or can use it optionally, from `source_info`'s per-source `credentials` (`required`), and shows **set** when keys.env holds every credential the account needs (either name of an alias pair is enough), **partly set** when it holds some (DataForSEO's login without its password), else **not set**, at the tile's top right; presence only, never validity. Below them, each local prerequisite `source_info` reports appears once with the sources that use it, **installed** or **not installed**. The list is hidden without `source_info` and refreshes with the page; the fold is built once, so a refresh rebuilds only its gist and contents and leaves it open or closed. It is view data only: no record or settings shape changed. A test requires every credential name `source_info` reports to belong to exactly one account, under its names or its optional ones, so a source's new key cannot be missing from the list.
- Each view's resource URI carries the package version (`ui://dig/library/v<version>.html`, `ui://dig/saved/v<version>.html`, built from `src/version.mjs`), because Codex caches a view by its URI: OpenAI's UI guide says to treat the resource URI as a cache key and publish a new one when the HTML, JavaScript or CSS changes. Every release changes the view bundle, so every release gets new URIs rather than a judgment about which changes break; the app-only tools name the same versioned URI as the entrypoints, and a test requires each tool's URI to be one the server lists. `library_snapshot` also carries the server's `version`, which is part of `library_revision`'s fingerprint, so a running view fetches a fresh snapshot after an update, and a view whose own version differs from the server's still shows a one-time notice to refresh it, in case a host keeps showing an older view anyway.
- Codex's installer removes the previous version's cache folder while the desktop keeps the old Dig server running. The server therefore reads both views once at startup and serves them from memory; reading them from disk on each request failed after an install, and the desktop reported "Couldn't refresh app". `library_snapshot`'s `replaced` (view data, also in the revision fingerprint) is null while the server's own package is in place and `{ version }` once it is gone, naming the newest version folder beside it (null after an uninstall). The view then says once, and About repeats, that the new version was installed while Codex was running and that quitting and reopening Codex loads it: Refresh only reloads the running server's own view. A replaced server's `source_info` still returns `skillPath`s inside the removed folder until Codex restarts it.
- Source logos live in `src/logos/` (from svgl, Simple Icons under CC0, and the Polymarket and Exa websites; they are trademarks of their owners, used to identify each service, with no affiliation claimed). The sandboxed view cannot load package files or outside images, so the build (`scripts/logo-sprite.mjs`) inlines them as one hidden SVG sprite of `<symbol>`s. It re-serializes each logo from an allowlist of shape and gradient elements, presentation attributes and CSS properties, prefixes its ids, turns simple class rules into inline styles and requires every `url()` and `href` to be a complete reference to an id the same logo defines. Anything else fails the build: another element or attribute (names are case-sensitive), unquoted values, text between tags, unbalanced tags or parentheses, CSS escapes or functions outside a short list, and outside references. Logos sit on a light tile in both themes. Sources without a usable logo (DeepWiki, Papers, China social, Commerce, DataForSEO) show their Dig glyph on the same tile.
- An exact-file deep link uses `codex://plugins/dig@<marketplace>/app/open_library?path=` plus the encoded app path `/read?file=<encoded-library-file>`. Activation refreshes the library before resolving the file, because a hidden view can hold an older snapshot. The file must belong to a dig in the selected library. Native acceptance was exercised through the OS URL handler, not URL entry in the embedded browser.

## Surfaces in the conversation

These read the existing research files and persist nothing (`src/surfaces.mjs`).

- **Open in Dig links.** `research_save`, `dig_finish`, each `library_list` item and `library_read` of a dig report or answer return `link`, the deep link above for that file. Codex passes the server no plugin id, so the server reads its identity from the installed cache layout `<cache>/<marketplace>/<plugin>/<version>/` and checks the manifest name. Outside an installed copy (repository, tests, preview) `link` is null rather than a guessed marketplace.
- **Saved-research card.** `research_save` and `dig_finish` declare the inline MCP App resource `ui://dig/saved/v<version>.html` (inline display, host border, no external domains). They are the one exception to OpenAI's advice that only render tools carry a view: each saves a file and shows the card once for that save, which is the card's purpose, so it does not cause the repeated re-rendering the advice guards against. The save result carries only the file; the card reads its details through the app-only `saved_research` tool: the question, the method label and glyph, the report's own source-card status or the answer's status as a tag, the opening of its `## Summary` (280 characters), retrievals claimed by that report (an answer counts all of its dig's retrievals), the save time and, for an answer, the reports it relies on. It offers **Open in Dig** through the host's link opener and, where the host provides a file opener, **Open file**. A host refusal is shown in the card. The card describes the save; it does not attest that the report was read.
- **Composer `@` mentions.** The mentions handler (app-only `search_mentions`) returns up to 20 saved reports and answers, newest first, whose question, method label or Summary opening contains every query word. Each is a `dig://library/<encoded file>` resource link, readable through the existing resource template. An attached mention is a pointer; the full-read rule for relied-on reports still applies. Source methods are invoked with `$`, not `@`.
- **Readiness button.** `source_readiness` groups enabled sources as ready, partly ready or needing setup, naming missing credential names and prerequisites, then lists disabled sources. It checks presence only and calls no provider.
